That is why nothing was bumped this session: applying an unverifiable eleven-major migration to a working released product for a 2-of-88 gain would be a bad trade. extract-zip is the other loose end - 2 alerts in electron/package-lock.json, entirely unpatched, so it needs a Dependabot ignore or a documented mitigation, and there is no .github/dependabot.yml in the repository at all, so adding that ignore means creating the config and thereby switching on Dependabot updates repo-wide, which is a policy decision rather than a one-line edit. Honest caveats about the tooling itself - the first triage run was wrong in three ways and all three are fixed and recorded here so the bad numbers are not trusted later. It labelled 212 alerts as an unknown severity because the script tested for "moderate" while the API field says "medium", which is also why the GitHub banner's wording does not match the field. It reported zero lockfile-backed criticals because uv.lock was missing from the lockfile list, when in fact all 16 criticals are lockfile-backed. And it ranked patched versions lexicographically, so '42.11.9' sorted above '42.11.16' and '7.5.8' above '7.5.18' and '3.9.4' above '3.10.4'; the printed targets for electron, tar and nltk were therefore too low, and acting on them would have left advisories unfixed. Version ranking now goes through packaging.version with a numeric-tuple fallback, and package names are case-folded, which also collapsed a phantom 40 distinct packages in the strix group to the real 35.
